# النقاط والمحفظة — الحالة الحالية

المتاح الآن: الأساس وثماني مهام آلية قابلة للتفعيل، عبر الترحيلات 025–029. جميع المهام موقوفة افتراضيًا لكل شركة. التحويل المالي وعمولة التصريف وأجور العمل لم تُنفذ. الأقسام الأولى أدناه توثق دفعة التأسيس؛ تفاصيل الوضع الحالي في الأقسام اللاحقة.

هذه الدفعة تنفذ الأساس الذي أذن به المستخدم بعد مراجعة الملف: محفظة موظف مستقلة داخل الشركة، سجل نقاط، إضافات إدارية موثقة وتصحيح بحركة عكسية، وكروت تعريف مهام المكافآت. التحويل المالي وعمولة التصريف وأجور العمل والاحتساب الآلي للأحداث دفعات تالية؛ لا تُفترض قيمة مالية للنقطة.

## المحفظة والسجل

الترحيل 025 ينشئ employee_wallets وemployee_wallet_entries. تُهيّأ جميع سجلات الموظفين الموجودة تلقائيًا بصفر، وإنشاء موظف جديد ينشئ محفظته داخل المعاملة نفسها. لا زر تهيئة ولا محفظة عامة خارج شركة. الحساب العام المرتبط بموظف في شركتين له محفظتان منفصلتان، والمالك دون سجل موظف لا يكتسب محفظة افتراضية.

الرصيد بالنقاط NUMERIC صحيح دقيق، ونقله في API نص؛ لا Number للكميات أو الجمع. مدخل النقاط يدعم الأرقام العربية والفارسية والفراغات والأصفار الأولية ويطبعها إلى نص صحيح عبر BigInt قبل المقارنة والتخزين. القيمة المالية في هذه الدفعة صفر فقط مع عملة الشركة الأساسية للعرض؛ قيد قاعدة البيانات يمنع إنشاء مستحق مالي قبل بناء السياسات الخاصة به.

السجل يحفظ موظف الشركة واسمه، الفاعل واسمه، النقاط، السبب، الوقت ومفتاح UUID. لا يتيح تعديل حركة أو حذفها أو ضبط الرصيد مباشرة. الرصيد يتغير عبر إدخال حركة سجل في معاملة واحدة، وتمنع قاعدة البيانات تحديثه خارج هذا المسار. العكس يرتبط بالمكافأة الأصلية ويقلب قيمتها كاملة في المحفظة نفسها مرة واحدة فقط؛ عكس العكس أو خصم يجعل الرصيد سالبًا مرفوضان. إضافة جزئية مصححة تتم بعكس الأصل ثم إضافة مكافأة جديدة بسبب واضح.

## الصلاحيات والطلبات

الموظف الفعال يرى محفظته وسجله فقط. المالك والمدير العام يختاران محفظة موظف داخل شركتهما ويضيفان نقاطًا بسبب إلزامي أو يعكسان إضافة سابقة. منح العرض لا يمنح الإضافة أو العكس. المدير يستطيع قراءة محفظة موظف مؤرشف بطلب معرفه؛ الإضافة والعكس الجديدان يخصان الموظفين الفعالين في هذه الدفعة. أرشفة الموظف تمنع دخوله ولا تمس سجل محفظته.

قواعد المنع الصريح وإتاحة الصفحات تفحص على الخادم، بما فيها مؤشر الرأس. الطلبات تحمل مفاتيح إعادة محاولة؛ مفتاح مقبول بنفس الفاعل والبيانات المطَبّعة يعيد الحركة نفسها دون زيادة أو تدقيق جديد، وتغييره ببيانات مختلفة يرجع 409. تأكيد طلب مقبول سابقًا يبقى ممكنًا بعد تعطيل الصفحة، مع استمرار التحقق من المستخدم والعضوية والإدارة. مفتاح جديد بعد التعطيل مرفوض. كتابة الحركة والرصيد والتدقيق قبل/بعد عملية واحدة؛ فشل التدقيق يلغي الجميع.

تحت /api/companies/:companyId:

- GET /wallet يعيد Page.items وسجل المحفظة المختارة، وwallet وemployees للإدارة وcanManage، مع بحث وترتيب وتصفح خادمي.
- GET /wallet/summary يعيد محفظة الموظف الحالي فقط أو null للمالك دون موظف.
- POST /wallet/awards يقبل employeeId وpoints وreason وidempotencyKey، ويعيد {entry}.
- POST /wallet/reversals يقبل entryId وreason وidempotencyKey، ويعيد {entry}.
- GET /reward-tasks يعيد الكروت والأدوار وصفحات الشركة المرجعية.
- PUT /reward-tasks/:code يحفظ قيمة النقاط وقاعدة التكرار والأدوار وصفحة الزيارة وrevision.

## كروت المهام

ثمانية تعريفات مبدئية قابلة للإعداد: حفظ المبيعات 5، المشتريات 10، سطور المبيعات 2، سطور المشتريات 0 لحين تحديدها، طلب طباعة قبض/صرف 5 لكل منهما، الدخول اليومي 50، وزيارة صفحة 0 لحين تحديدها. القيم ليست سعر تحويل مالي. التعريفات تظهر كمخططة وموقوفة؛ تفعيلها مرفوض في API وقاعدة البيانات إلى حين ربط الأحداث الفعلية في الدفعة التالية.

قواعد التكرار المحفوظة: لكل مستند، يوميًا، خلال سبعة أيام، وغير محدود. ربط الأدوار يراجع أدوارًا فعالة من الشركة نفسها؛ ربط الصفحة يخص مهمة PAGE_VISIT ويقبل صفحة شركة مسجلة فقط. التعديلات تحمل إصدارًا وتدقيقًا؛ تعديل التعريف لا يعدل حركة نقاط سابقة. عند بناء الربط الآلي ستثبت السياسة الخاصة بتجميع مكافأة الفاتورة والسطور، ومنع تضاعف المكافأة بسبب تقسيم السطر. يُحافظ على طلب المستخدم أن سطور المردودات تستحق نقاطًا مثل الموجب. الدخول العام مقابل الشركات يحتاج تحديدًا قبل منحه نقاطًا داخل شركة.

## الواجهة والتحقق

المحفظة ومهام المكافآت مسجلتان في دليل الصفحات والقائمة. يظهر مؤشر النقاط بجوار التنبيهات داخل الشركة للموظف المرتبط فقط، بكاش مستخدم/شركة/موظف وتحديث كل 30 ثانية عندما تكون الصفحة ظاهرة. مؤشر الرأس يعرض محفظة المستخدم نفسه حتى عند اختيار المدير موظفًا آخر في قائمة المحفظة. القراءة والإضافة والعكس تحفظ نطاق الطلب وتدعم RTL والجوال.

نجح اختبارا API محددان: أرقام أكبر من المجال الصحيح الآمن في JavaScript، التزامن وإعادة الطلب، العكس الواحد وحماية السجل والرصيد، تراجع العملية عند فشل التدقيق، الصلاحيات والعزل والعضوية والتعطيل، وحماية كروت المهام والمراجع والإصدارات. نجح فحص متصفح واحد للإضافة بأرقام عربية، ظهور 20 نقطة للموظف، العكس إلى صفر مع بقاء الحركتين، وإعداد مهمة مخططة دون تفعيلها. نجح TypeScript وبناء الواجهة؛ لم تشغّل مجموعات المشروع العامة.

## التالي

1. عمولة التصريف بعد تحديد أساس القيمة ومعالجة المردود.
2. تحويل النقاط بعد تحديد قيمة النقطة والعملة والاعتماد وحسابات القيد؛ لا يسمح بالتحويل قبل اكتمال هذه السياسات.

## الدفعة الثانية — مكافآت الفواتير وسطورها

ترحيل 026 يفعّل إمكان **اختيار تشغيل** أربع مهام على مستوى كل شركة: SALE_SAVED وPURCHASE_SAVED وSALE_LINES وPURCHASE_LINES. تبقى كل المهام موقوفة افتراضيًا، ولا تُمنح مكافآت على الفواتير السابقة. بعد التفعيل تتطلب المهمة قاعدة «لكل مستند»، وتُراجع أدوار الموظف الفعالة إن اختارت الإدارة أدوارًا محددة؛ فارغ الأدوار يعني جميع الموظفين الفعالين.

يُستدعى `awardPostedInvoice` داخل معاملة `createInvoice` بعد ترحيل القيود وربط الفاتورة بها وقبل تدقيق `invoice.post`. المستخدم الذي لا يملك سجل موظف فعالًا في الشركة لا يحصل على مكافأة. لكل مهمة مفعّلة حركة مستقلة في دفتر المحفظة، مع رقم الفاتورة ونوع المهمة وإصدار الإعداد وقيمة النقاط لكل وحدة وعدد الوحدات وقيمة النقاط النهائية. يُمنع تكرار منح الموظف لنفس الفاتورة والمهمة بفهرس فريد؛ كما يُعيد مفتاح الفاتورة نفسه الفاتورة الأصلية قبل الوصول لمنح أي نقاط.

تُحتسب سطور الفاتورة بحساب المجموعات الفريدة من **الصنف + الوحدة + السعر + دفعة تاريخ الصلاحية**، لذلك لا يزيد عدد المكافآت إذا قُسمت كمية الصنف بالمواصفات نفسها إلى صفوف متعددة. تتراكم مكافأة الفاتورة المستقلة مع مكافأة سطورها عند تفعيل الاثنين. السطور في المردودات تحتسب كمكافأة عمل موجبة، وليست عمولة مالية سالبة؛ لا ربط مالي في هذه الدفعة. لا تُعطى حركة قيمتها صفر. تغيير الإعداد لا يعيد تسعير أي استحقاق سابق.

تتيح واجهة السجل عرض المهمة والمكافأة والتوجه للفاتورة عند امتلاك صلاحية العرض، كما تسمح الإدارة بعكس مكافأة آلية لم تُعكس سابقًا بشرط كفاية النقاط. يحفظ العكس حركة مقابلة ولا يحذف الأصل، مع السبب ومستخدم التصحيح. عمولة تصريف الأصناف والتحويل المحاسبي مؤجلان إلى حين تحديد السياسة المالية.


## الدفعات اللاحقة — الطباعة وزيارة الصفحة ودخول الشركة

الترحيل 027 يربط طلب طباعة سند القبض أو الصرف المرحل بمكافأة واحدة لكل موظف ولكل سند، حتى عند تكرار الطلب أو عكس مكافأته إداريًا. الطلب لا يثبت خروج الورقة فعليًا. الخادم يتحقق من العرض والطباعة والعضوية الحالية والأدوار المؤهلة؛ منع الإضافة وحدها لا يمنع الطباعة، والمسودة والسند المعكوس لا يستحقان. المسار POST /companies/:companyId/financial-documents/:id/print-request يعيد {rewarded, entryId}.

الترحيل 028 يربط PAGE_VISIT بصفحة شركة واحدة محددة في الكرت، بعد التحقق من إتاحتها وصلاحية عرضها. الواجهة ترسل حدث انتقال فعلي، ولا تمنح نقاطًا عند تحديث بيانات الخلفية. التكرار اليومي حسب يوم عدن، والسبعة أيام نافذة متحركة كاملة. الزيارات المتكررة لها فاصل 15 ثانية وسقف يومي افتراضي 100 استحقاق إذا لم تحدد الإدارة سقفًا؛ اسم «غير محدود» لا يعطل هذه الحماية. المسار POST /companies/:companyId/reward-events/page-visit يقبل pageKey وidempotencyKey ويعيد {rewarded}. إعادة الحدث المقبول لا تزيد الرصيد؛ استعمال مفتاحه لمستخدم آخر أو صفحة مختلفة أو عملية أخرى يرجع 409.

الترحيل 029 يمنح DAILY_LOGIN مرة واحدة يوميًا عند دخول الموظف فعليًا إلى مساحة الشركة حسب Asia/Aden، داخل معاملة تفعيل الشركة. الدخول العام لا يوزع نقاطًا على جميع عضوياته. تكرار الفتح والتبويبات وتغيير قيمة المهمة في اليوم نفسه لا يمنح استحقاقًا ثانيًا. الواجهة تثبت قاعدة «مرة يوميًا» لهذه المهمة.

كل المهام الثماني أصبحت منفذة وقابلة للتفعيل، مع بقاء الافتراضي موقوفًا. مكافآت الفواتير والطباعة تستخدم «لكل مستند» فقط، والدخول «يوميًا» فقط. زيارة الصفحة تتطلب صفحة ونقاطًا موجبة وقاعدة زمنية. تعديل الإعداد لا يغير حركة سابقة ولا يستحق بأثر رجعي.

## مراجعة المتابعة بعد PR #40

PR #40 أضاف فحوص API وCI معزولة للمهام الثماني، ولم يغير منطق الإنتاج أو إعدادات Railway. مراجعة المتابعة أصلحت صلاحيات طلب الطباعة، والتعارض عند إعادة مفتاح زيارة بمستخدم أو صفحة أخرى، والنصوص القديمة التي كانت تصف المهام المنفذة بأنها مخططة. أصبح السجل يميز أنواع المكافآت الآلية، ويُحدث الرصيد والسجل في نطاق المستخدم والشركة بعد الاستحقاق، مع بقاء التحديث الدوري كل 30 ثانية.

التحقق المركز يخص مسار المحفظة والمهام والأرصدة والصلاحيات المرتبطة بالإصلاحات، مع TypeScript والبناء؛ لا يعادل اختبار جميع شاشات الموقع. تبقى قيمة النقطة والعملة والاعتماد وحسابات قيد التحويل، وأساس عمولة التصريف ومعالجة المردود، سياسات غير محسومة قبل تنفيذ التحويل المالي.
