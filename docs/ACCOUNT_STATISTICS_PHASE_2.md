## نطاق هذه الدفعة

هذه الدفعة تنشئ التخزين المستقل الذي تعتمد عليه مراحل احتساب الأرصدة والحركات والفترات ثم العرض. يبقى نطاق المؤشرات 50 بندًا: حذف «الصنف من المورد» من جدول الحسابات دون تغيير كرت الصنف، وإلغاء «خصائص التعديل الآلي للحسابات». الأسبوع يبدأ السبت. قيمة الأصناف للحساب ستتبع مورد الكرت الحالي مع متوسط تكلفة المخزون المعتمد ووسم `supplierInferred`.

لا توجد في هذه الدفعة معادلات أو تعبئة تاريخية للمؤشرات أو API أو حقول واجهة جديدة؛ حالات التخزين تفرق صراحة بين تهيئة السجل واحتساب قيمه. إنشاء الصف لا يثبت أن رصيد الحساب صفر أو أنه جرى اعتماده أو متابعته.

## الجداول

| الجدول                      | الغرض في هذه الدفعة                                                                                       | التهيئة                                                         |
| --------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `account_statistics`        | هوية شركة/حساب حركي، إصدار سياسة، وإصدار مصدر وحالة احتساب مستقلة للأرصدة والنشاط والتجارة والمخزون       | صف للحسابات الحركية القديمة والجديدة؛ جميع الأجزاء `uncomputed` |
| `account_daily_activity`    | هيكل تجميع يومي حسب الشركة والحساب والتاريخ والعملة وعائلة المصدر، مع مبالغ دقيقة وإصدار مصدر             | فارغ؛ لا أيام أو أصفار مصطنعة                                   |
| `account_balance_followups` | سجل متابعة بشري مستقل: وقت متابعة، فاعل، ملاحظة، وقت حفظ وهوية إعادة طلب                                  | فارغ؛ لا استنتاج أحداث سابقة من فتح الكرت أو الحركات            |
| `account_balance_approvals` | لقطة اعتماد ثابتة: حد تاريخ الرصيد، مبلغ أساسي موقع، عملة ودقتها، فاعل وإصدار سياسة ومصدر وهوية إعادة طلب | فارغ؛ لا توليد اعتماد من الرصيد أو آخر حركة                     |

`initialize_account_statistics(company_id,account_id)` يدرج الحساب الحركي فقط، ويستخدم `ON CONFLICT DO NOTHING`؛ إعادة تشغيله تحفظ السجل الموجود وتواريخه وحالته. مشغل إنشاء الحساب يهيئ صفه في المعاملة نفسها. لا تتحول حسابات المجموعة إلى حسابات ذات رصيد مباشر.

الحسابات تُنشأ قبل العملات عند تأسيس الشركة؛ لذلك لا يشترط الملخص عملة أساسية غير فارغة أثناء التهيئة. اليوميات ولقطات الاعتماد التي تحمل مبالغ ترتبط بعملة من الشركة نفسها عند إدراجها لاحقًا.

## دلالة الجاهزية

للملخص أربع مجموعات مستقلة: `balance` و`activity` و`commerce` و`stock`. لكل منها حالة وإصدار احتساب وتاريخ نطاق ووقت احتساب.

- `uncomputed`: لم يحتسب الجزء. إصدار احتسابه وتاريخه ووقته `NULL`.
- `ready`: metadata مكتملة وإصدار الاحتساب يطابق إصدار المصدر المخزن. وجود الحالة لا يحل محل فحص تاريخ التقرير أو صلاحية العرض عند بناء API لاحقًا.
- `stale`: توجد عملية احتساب سابقة، لكنها لا تعرض كقيمة حديثة. تبقى metadata محفوظة لتفسير قدمها.

تبدأ `source_revision` بصفر بوصفها أساسًا تعاقديًا فقط. هذه الدفعة لا توصلها بمصادر الفواتير والدفتر والمخزون، ولا تعتبر الصفر إثباتًا لعدم وجود تاريخ. محرك المرحلة اللاحقة سيحدث المصدر والمجاميع والحالة في معاملة متسقة، مع ترتيب قفل المستخدم ثم الشركة ثم السجلات.

المفتاح الفريد للتجميع اليومي يمنع تكرار صف bucket، لكنه لا يمنع وحده إعادة جمع المستند نفسه. عند تنفيذ المحرك يلزم اشتقاق حتمي من المصدر أو هوية حدث ثابتة، وإزالة ازدواج الفاتورة مع قيودها الرئيسية والتكلفة والفروق وفق المرحلة الأولى.

عائلات اليوميات هي `ledger/activity/sale/purchase/purchase_cash/payment/receipt`. عائلة `purchase_cash` جزء من المشتريات لخدمة مؤشر المشتريات النقدية؛ لا تجمع مع `purchase` لاستخراج إجمالي المشتريات. كذلك لا تجمع عدادات العائلات لاستخراج عدد الحركات العام؛ له عائلة `activity` المستقلة.

## العزل والتاريخ

- المفاتيح الأجنبية مركبة بالشركة، واليوميات والمتابعة والاعتماد ترتبط بالحساب الحركي نفسه. لا يمكن إسناد عملة من شركة أخرى.
- المبالغ `NUMERIC(38,6)` موقعة حيث تسمح طبيعتها، وعدد المستندات `BIGINT` غير سالب. العقود المشتركة تحفظ المبالغ والإصدارات الدقيقة كنصوص عند استخدامها لاحقًا.
- إدراج اعتماد يتحقق من أن معرّف العملة هو الأساسية الفعلية للشركة وأن الكود والدقة في اللقطة يطابقانها؛ لا يمكن تثبيت مبلغ بدقة أو تسمية عملة مخالفة ثم جعله غير قابل للتعديل.
- المتابعة والاعتماد سجلان ملحقان ثابتان؛ يمنع تحديثهما أو حذفهما. UUID فريد داخل الشركة، ويحفظ الفاعل والطلب المطبع لتطبيق تطابق إعادة الطلب لاحقًا. قاعدة البيانات لا تمنح من نفسها إذن إجراء لمستخدم.
- لقطة الاعتماد مستقلة عن فاتورة أو سند مفرد؛ لا ينشأ مفتاح أجنبي جديد يعوق حذف المصادر عبر الصيانة المعتمدة. لا تحذف الصيانة الحالية سجل متابعة أو اعتماد؛ قبل تشغيل واجهات الاعتماد يجب تحديد معنى الاعتماد من جيل مصدر سابق بعد reset، مع بقاء اللقطة تاريخية ثابتة.
- لا تُنسخ الخيارات المخصصة إلى سجل متابعة ولا يُستبدل خيار موجود باسمه فقط. فحص تعريفات الشركة قبل ربط حقل الكرت يبقى خطوة لازمة في مرحلة الواجهة/إجراء المتابعة.
- لا تتغير قواعد الأرصدة الحالية أو الفواتير أو السندات أو المخزون أو الصلاحيات أو صفحات الموقع. لا يوجد مسار جديد يعرض الجداول قبل بناء صلاحيات أجزائه.

## التحقق

الفحص المركز يغطي الترقية من قاعدة عند 074 إلى 085، وتهيئة القديم والجديد ونوع الحساب، وإعادة التهيئة دون محو، وغياب الأحداث والمجاميع المصطنعة، وقيود حالات الجاهزية، وعزل الشركات والحسابات والعملات، ودقة المبالغ، وثبات سجلات المتابعة والاعتماد وعدم تكرار UUID داخل الشركة.

قاعدة الفحص محلية أو خدمة CI محلية باستخدام متغير اختبار خاص، مع schema عشوائي يزول بعد الاختبار؛ لا يستخدم الاختبار `DATABASE_URL` العام. فحص تأسيس الشركة القائم شُغّل مع فرض عنوان قاعدة الاختبار المحلية صراحةً.

## ما يلي هذه المرحلة

المرحلة الثالثة تضيف احتساب الأرصدة التاريخية وإجراءات المتابعة والاعتماد بحسب العقد المعتمد، ثم تليها الحركات والفترات وقيمة الأصناف والتحديث والعرض وفق ترتيب الخطة. توصيل محفزات المصدر وإعادة البناء وصيانة الإسقاطات يسبق إظهار حالة `ready`. رصيد دفتر الحساب الفعلي يبقى من القيود الأصلية المعتمدة.
