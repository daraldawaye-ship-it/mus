# نشر النسخة الحالية

الحاوية تقدم الواجهة وAPI معًا، وتحتاج قاعدة PostgreSQL خارجها وبوابة HTTPS أمامها. اختار المستخدم Railway بعد تعذر إكمال تسجيل Render، وربط مستودع GitHub وخدمة PostgreSQL. يبقى Dockerfile قابلًا للنقل بين خدمات Docker. رفع الشفرة أو بدء نشر تلقائي لا يثبت نجاح الموقع؛ يجب التحقق من رابط HTTPS الفعلي وسجل النشر.

## النشر على Railway

المشروع الموجود هو `abundant-possibility`، والبيئة `production`، وخدمة التطبيق `mus` وقاعدة البيانات `Postgres`. لا تنشئ مشروعًا أو قاعدة بديلة لمجرد تحديث التطبيق. المستودع `daraldawaye-ship-it/mus`، والفرع المتصل `codex/deploy-phase2`. اسم الفرع تاريخي ويمكن أن يحتوي المراحل اللاحقة أيضًا؛ رفع التحديثات إليه يبدأ النشر تلقائيًا بحسب الإعداد الذي اختاره المستخدم.

رابط التطبيق الذي أنشأه المستخدم: `https://mus-production.up.railway.app`. وجود الرابط لا يثبت أن آخر نشر نجح. إعدادات خدمة التطبيق:

| الإعداد | القيمة |
| --- | --- |
| Source branch | `codex/deploy-phase2` |
| Root directory | جذر المستودع |
| Dockerfile | `Dockerfile` في الجذر؛ اكتشافه التلقائي يكفي |
| Custom Build Command | فارغ؛ البناء داخل Dockerfile |
| Custom Start Command | فارغ؛ الأمر الافتراضي `npm start` داخل الصورة |
| Pre-deploy command | فارغ في التشغيل المعتاد |
| Healthcheck Path | `/api/health` |
| Healthcheck Timeout | `300` ثانية |
| Domain target port | `3000` |

تُضبط المتغيرات داخل خدمة `mus`، لا داخل `Postgres`:

| Name | Value |
| --- | --- |
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}`؛ مرجع إلى رابط القاعدة الداخلي |
| `APP_ORIGIN` | `https://mus-production.up.railway.app` |
| `PORT` | `3000` |

يتطلب اسم المرجع اسم خدمة قاعدة البيانات الفعلي. لا تستبدل الرابط الداخلي بالرابط العام ولا تنسخه إلى Git. الحاوية تضبط `NODE_ENV=production` و`HOST=0.0.0.0` وتطبق الترحيلات عند البدء. تحتفظ خدمة PostgreSQL وقرصها بالبيانات عند استبدال حاوية التطبيق.

بعد حفظ تغييرات إعدادات Railway، اضغط **Deploy** لتطبيق التغييرات المعلقة إن ظهرت. عند فشل البناء، افتح **Deployments → View logs** لمعرفة الخطأ الفعلي؛ إعدادات المنفذ والقاعدة لا تعالج خطأ تحقق Dockerfile. يستخدم الملف أوامر Docker المعتادة و`npm ci` دون `RUN --mount` أو أسرار بناء خاصة بمنصة واحدة.

### الوصول الآلي من Codex

دفع Git يستعمل اتصال GitHub الموجود في البيئة ويمكن أن يبدأ نشر Railway التلقائي. قراءة الموقع وفحص الصحة تحتاج السماح بالوجهة `mus-production.up.railway.app` في إعدادات شبكة بيئة Codex. قراءة حالة النشر وسجلاته أو إعادة نشره عبر API تحتاج اتصالًا مصرحًا بحساب Railway وإتاحة الوجهة الرسمية `backboard.railway.com`.

إذا كان الربط عبر API مطلوبًا، يُدخل المستخدم `RAILWAY_API_TOKEN` في حقل الأسرار الآمن لبيئة Codex، بوجهة `backboard.railway.com`، ولا يرسله في المحادثة أو يضعه في متغيرات خدمة التطبيق. تستخدم واجهة Railway الرسمية `https://backboard.railway.com/graphql/v2` رمز حساب API في رأس `Authorization: Bearer …`. رمز مشروع Railway له رأس ومجال صلاحية مختلفان؛ لا تفترض أن الرمز الذي قدمه المستخدم من نوع الحساب دون التحقق من نوعه. لا يحتاج التطبيق نفسه رمز Railway.

حفظ مسودة إعدادات Codex لا يفعّل الشبكة أو الأسرار ولا ينشر التطبيق. إذا أشارت أداة الإعداد إلى `requires_publish`، تراجع الإعدادات وتحفظ ثم تنشر البيئة لتفعيلها. رفض نفق الاتصال قبل استجابة HTTP من الموقع لا يثبت أن الموقع متوقف.

### إنشاء المالك مرة واحدة

إذا كان المالك موجودًا فلا تنفذ خطوة إنشاء جديدة. عند توفر طرفية خدمة فعلية استخدم `npm run owner:create` كما هو موضح أدناه. تدعم النسخة أيضًا اعتماد حساب مسجل ونشط مرة واحدة عبر `/setup-owner` عندما يُضبط مؤقتًا `OWNER_SETUP_TOKEN` في Railway. لا تظهر هذه الصفحة إلا عند عدم وجود مالك ووجود رمز تهيئة صالح بطول 43–128 من أحرف base64url. يلزم تسجيل الدخول والحصول على CSRF ورمز التهيئة الصحيح؛ تسجيل المستخدم الأول لا يمنحه الملكية تلقائيًا.

ضع رمزًا عشوائيًا قويًا في إعدادات Railway الآمنة، ثم افتح `/setup-owner` بحساب المستخدم المقصود وأدخله في حقل الصفحة. بعد نجاح الاعتماد احذف `OWNER_SETUP_TOKEN` من إعدادات الخدمة وأعد النشر. لا ترسل الرمز إلى المحادثة، ولا تحفظه في المستودع، ولا تتركه مفعّلًا لاستخدام مستقبلي.

عند استخدام مهمة مؤقتة لـ`npm run owner:create` عبر متغيرات `OWNER_EMAIL` و`OWNER_NAME` و`OWNER_PASSWORD`، احذف المتغيرات وأمر pre-deploy بعد نجاح المهمة، حتى لو احتاج تشغيل الويب لاحقًا إصلاحًا آخر. الأمر يرفض المالك الثاني؛ إبقاؤه ضمن كل نشر يمنع التحديثات التالية. لا تضع أي أمر إنشاء مالك ضمن Dockerfile أو البدء المعتاد.

## النشر على Render

إعداد الموارد في [render.yaml](../render.yaml). يبدأ النشر من نسخة المشروع المحفوظة في Git والمرفوعة إلى مستودع يستطيع Render قراءته:

يقترح الملف خدمة ويب بخطة `starter` وقاعدة PostgreSQL بخطة `basic-256mb` في منطقة `frankfurt` للخدمتين. الخطتان مدفوعتان؛ قاعدة البيانات مستقلة وتحتفظ بالبيانات عند إعادة نشر التطبيق. راجع التكلفة الحالية وحجم تخزين القاعدة المعروض في حسابك قبل التطبيق، وزد موارد القاعدة عند الحاجة. يمنع `ipAllowList: []` الاتصالات الخارجية بقاعدة البيانات، ويستخدم التطبيق رابطها الداخلي.

1. من لوحة Render اختر إنشاء **Blueprint**، ثم مستودع `daraldawaye-ship-it/mus` وفرع `codex/deploy-phase2` الذي يحتوي النسخة الحالية. عند ربط مستودع خاص امنح Render الوصول إليه عبر GitHub من حسابك.
2. راجع نتيجة فحص Blueprint وخطتي خدمة الويب وPostgreSQL والتكلفة المعروضة قبل إنشاء الموارد المدفوعة. استعمل منطقة واحدة للخدمتين؛ توفر قاعدة البيانات رابطها الداخلي لخدمة الويب.
3. طبّق الإعداد بعد اعتماد التكلفة. يبني Render الصورة من Dockerfile، ويبدأ API والواجهة، ويفحص `/api/health`.
4. افتح رابط HTTPS الذي توفره الخدمة، ثم تحقق من الصفحة العربية والجلسة والتنقل إلى رابط مباشر.

عند استعمال نطاق Render الأولي، يأخذ التطبيق مصدره من `RENDER_EXTERNAL_URL` الذي توفره المنصة. إذا ربطت نطاقًا مخصصًا، اضبط `APP_ORIGIN` على مصدره النهائي عبر HTTPS بعد تفعيل شهادة TLS. `DATABASE_URL` يأتي من ربط PostgreSQL في Blueprint؛ لا تكتبه في المستودع.

لإنشاء المالك افتح **Shell** الخاصة بخدمة الويب المدفوعة، ثم نفذ من `/app`:

```sh
npm run owner:create
```

أدخل الاسم والبريد وكلمة المرور عند الطلب. راجع تفاصيل التحقق وكلمة المرور أدناه. لا توجد حاجة إلى متغيرات مالك دائمة أو كلمة مرور افتراضية. التحديثات تستعمل قاعدة البيانات نفسها؛ راجع سياسة النشر التلقائي في الخدمة، ولا تنشر مرحلة جديدة قبل فحوصها.

يضبط Blueprint قيمة `autoDeploy: false`، لذلك تبقى التحديثات اللاحقة بنشر يدوي من لوحة الخدمة بعد رفع النسخة المجتازة للفحوص. عند توفر Render CLI وحساب متصل ومساحة عمل محددة، يمكن فحص الملف قبل إنشاء الموارد باستخدام `render blueprints validate render.yaml` من جذر المشروع. فحص YAML محليًا وحده لا يثبت قبول Render للخطط والإعدادات، ولا يعني أن الموقع نُشر.

## البناء والتشغيل

من جذر المشروع، في جهاز أو خدمة تدعم Docker:

```sh
docker build -t tijara:0.3.0 .
```

يبني Docker الواجهة باستخدام Node 24.19.0 وملف القفل، ثم يثبت اعتماديات الإنتاج فقط. تعمل الحاوية كمستخدم `node` دون صلاحيات root. تتضمن ملفات API والعقود وترحيلات SQL والواجهة المبنية؛ قاعدة البيانات وبيانات الاعتماد خارج الصورة.

أنشئ PostgreSQL مستقلة ودائمة، واستعمل رابط الاتصال الذي توفره الاستضافة مع إعداد TLS المعتمد لديها. يحتاج مستخدم قاعدة البيانات صلاحية إنشاء الجداول وتطبيق الترحيلات داخل النطاق المختار. لا تنقل قاعدة الاختبارات المحلية إلى الإنتاج.

اضبط القيم من إعدادات المتغيرات والأسرار في الاستضافة:

| المتغير | القيمة المطلوبة |
| --- | --- |
| `DATABASE_URL` | رابط PostgreSQL الخاص بالإنتاج؛ يُحفظ كسر |
| `APP_ORIGIN` | مصدر HTTPS النهائي فقط، مثل `https://example.com`، دون مسار أو بيانات دخول؛ يمكن أن توفره `RENDER_EXTERNAL_URL` على Render |
| `DATABASE_SCHEMA` | اختياري؛ الافتراضي `public` |
| `PORT` | الافتراضي `3000`؛ يمكن تغييره إذا فرضت الاستضافة منفذًا آخر |

الصورة تضبط `NODE_ENV=production` و`HOST=0.0.0.0`. افتح منفذ التطبيق لبوابة الاستضافة، واربط النطاق وأصدر شهادة TLS. توجّه البوابة الواجهة و`/api` إلى الحاوية نفسها. يجب أن يصل رأس `Origin` الأصلي للطلبات دون استبداله؛ طلبات التعديل تتحقق منه، والجلسات تستعمل ملفات تعريف ارتباط `Secure`.

على خادم Docker، يمكن حفظ المتغيرات في ملف خارج المستودع بصلاحيات قراءة مقيدة، ثم تشغيل الحاوية خلف بوابة HTTPS:

```sh
docker run -d --name tijara --restart unless-stopped --init \
  --env-file /secure/path/tijara.env \
  -p 127.0.0.1:3000:3000 tijara:0.3.0
```

استبدل مسار الملف بمساره الفعلي. هذا الربط مخصص لبوابة تعمل على الخادم نفسه؛ خدمات الحاويات المدارة تتولى توجيه المنفذ من إعداداتها. لا تضع الأسرار في Dockerfile أو Git أو أوامر محفوظة في سجل الطرفية.

## التحقق وإنشاء المالك

يفحص Docker `/api/health` تلقائيًا. بعد توجيه النطاق، تحقق من أن `https://example.com/api/health` يعيد `{"ok":true}`، وأن الصفحة العربية والدخول والرابط المباشر لإحدى الصفحات يعملان عبر HTTPS. استبدل النطاق بالنطاق الحقيقي، وراجع سجلات الحاوية عند فشل البدء.

لا يوجد مالك أو كلمة مرور افتراضية. أنشئ المالك مرة واحدة داخل طرفية تفاعلية تتصل بالحاوية وقاعدة الإنتاج:

```sh
docker exec -it tijara npm run owner:create
```

يطلب الأمر الاسم والبريد وكلمة المرور مع إخفائها وتأكيدها. كلمة المرور لا تقل عن 12 حرفًا، ويُرفض إنشاء مالك ثانٍ. في خدمة مدارة استخدم طرفيتها التفاعلية لتنفيذ `npm run owner:create` من `/app`. عند الحاجة إلى تشغيل آلي، حقن `OWNER_EMAIL` و`OWNER_NAME` و`OWNER_PASSWORD` عبر مدير الأسرار في مهمة مؤقتة فقط؛ لا تحفظها ضمن متغيرات خدمة الويب الدائمة ولا ترسلها في المحادثة.

## تحديث النسخة

تبقى PostgreSQL نفسها عند استبدال صورة التطبيق. تُطبق الترحيلات عند البدء، وتُسجل إصداراتها في `schema_migrations`؛ لا تعيد تهيئة قاعدة البيانات ولا تعدّل ترحيلًا سبق تطبيقه. قبل تحديث يمس البيانات، احفظ نسخة احتياطية قابلة للاستعادة، ثم ابنِ صورة بإصدار جديد، حدّث الخدمة، وتحقق من الصحة والدخول عبر النطاق. الرجوع إلى صورة أقدم لا يلغي ترحيلات قاعدة البيانات تلقائيًا.

يُسجل نجاح كل تحديث بعد فحص النطاق العام وحالة النشر الفعلية. في Railway الموجود، رفع الفرع المتصل يبدأ النشر التلقائي بحسب إعداد الخدمة. في Render، تطبق الخطوات أعلاه إذا اختاره المستخدم لاحقًا. إنشاء الملفات محليًا لا يرفعها إلى المستودع أو ينشئ موارد الاستضافة.

## التحقق المحلي — 2026-10-11

هذه نتائج نسخة الأساس السابقة لمرحلة القيود والسندات: اجتاز المشروع فحص الأنواع و40 اختبارًا آليًا، وسبق نجاح 15 سيناريو متصفح لهذه الواجهة. بُني Dockerfile حينها وشُغلت الصورة بمستخدم `node` واعتماديات إنتاج دون Vite، على نطاق PostgreSQL معزول. نجحت الترحيلات والصحة والصفحة العربية والروابط المباشرة وملفات البناء والتسجيل وحماية المصدر وCSRF وسمات الجلسة. نجح أمر إنشاء المالك ورُفض تكراره، وبقيت البيانات والجلسة بعد إعادة تشغيل الحاوية. لا تحل هذه النتائج التاريخية محل فحوص مرحلة جديدة أو تحقق نشرها.

نجح فحص صياغة YAML ومراجع قاعدة البيانات محليًا. لم يُنفذ فحص Blueprint لدى Render أو إنشاء مواردها أو فحص TLS عبر نطاق عام؛ هذه الخطوات تحتاج حساب الاستضافة. أسماء الخطط والتكلفة النهائية تُراجع في معاينة Blueprint قبل تطبيقها.

### تحقق حاوية مرحلة المحاسبة — 2026-10-11

اجتاز Dockerfile الحالي فحص BuildKit دون تحذيرات صياغة. واجه تثبيت npm داخل البناء المحلي شهادة وسيط شبكة البيئة، فأُضيفت شهادة الثقة الموجودة إلى نسخة Dockerfile مؤقتة خارج المستودع عبر secret mount لخطوتي npm فقط. بقي التحقق من TLS وملف القفل مفعّلًا، وبقي Dockerfile الذي تستعمله Railway دون هذه الإضافة المحلية. لا يعد ذلك نجاحًا لبناء Railway نفسه؛ قراءة سجله الفعلي ما زالت مطلوبة.

بُنيت صورة `tijara:0.3.0` بفحص الأنواع والواجهة المبنية، وشُغلت بمستخدم uid 1000 واعتماديات إنتاج دون Vite، ودون ملف شهادة الثقة المؤقت داخل حاوية التشغيل. على نطاق PostgreSQL محلي معزول، نجحت الترحيلات الخمسة بما فيها `005_accounting.sql`، وفحص الصحة والواجهة العربية والرابط المباشر وسمات جلسة الإنتاج. أنشأ الفحص سند قبض تجريبيًا بمبلغ دقيق `1.25` ورحله، ثم تحقق من الرصيد وكشف الحساب. بقيت الجلسة والمستند والرصيد بعد إعادة تشغيل الحاوية. حُذفت الحاوية ونطاق الفحص بعد إتمام التحقق، دون تعديل بيانات الإنتاج.
