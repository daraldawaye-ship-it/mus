## قاعدة تنفيذ التعديلات

طلب المستخدم تعديلًا أو إصلاحًا أو إضافة يتضمن الإذن باختباره ودمجه في فرع الإنتاج ونشره على الخدمة المحددة أعلاه، ما لم يطلب صراحةً عدم النشر. لا تطلب تأكيد نشر منفصلًا.

1. تحقق من أدوات GitHub وRailway والفرع والنسخة المنشورة، واستعمل البيانات المؤكدة هنا قبل طلب معلومات من المستخدم.
2. نفذ تعديلًا محددًا يحفظ الميزات السابقة، ثم شغّل الفحوص والاختبارات المناسبة للتغيير.
3. ادمج التعديل في `codex/deploy-phase2` مع الحفاظ على أحدث التعديلات، وتابع نشر المصدر الجديد على خدمة `mus` في `production`.
4. لا تصف التعديل بأنه منشور قبل مشاهدة Railway `SUCCESS` والتحقق من نجاح `/api/health`. إنشاء commit أو PR أو نجاح رفع المصدر لا يثبت النشر.
5. افحص السجلات وأصلح فشل البناء أو النشر وأعد المحاولة عندما يكون ذلك ممكنًا وآمنًا. عند وجود عائق، اذكر السبب الفعلي وما تم وما بقي.
6. حافظ على قاعدة البيانات والإعدادات والوظائف السابقة. لا تعد إلى إصدار قديم ولا تحذف بيانات أو تنفذ تغييرًا مدمرًا دون موافقة صريحة.
7. قدم تقريرًا مختصرًا يتضمن التغيير ونتيجة الاختبارات وحالة Railway ورابط الموقع.

**كل تعديل مكتمل = تنفيذ + اختبار + دمج + نشر + تحقق.**

## الهوية والتوافق

تستخدم النصوص الظاهرة للمستخدم اسم «الرئيسي» أو «الرئيسي | Alraesy». تبقى معرفات المستودع والاستضافة، وأسماء أدوات MCP ونطاقات OAuth، وصيغ الاستيراد، ومفاتيح الجلسات والتخزين، وأسماء قاعدة البيانات ثابتة لضمان التوافق. وجود `tijara` في هذه المعرفات أو في المراجع التاريخية لا يعني ظهور هوية «تجارة» في الواجهة. اسم الإضافة وعرضها في ChatGPT إعدادات مستقلة عن أكواد الموقع.
